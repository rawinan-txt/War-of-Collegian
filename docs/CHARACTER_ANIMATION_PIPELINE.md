# Character Animation Pipeline

Status: **approved design** (see section 6), plus as-built analysis. Nothing in this document changes gameplay. Section 1 describes how Bug Hunter works today (verified against the repository at commit `6dd6858`), section 2 lists what blocks scaling to ~100 characters, section 3 is the proposed data-driven architecture, section 4 is the add-a-character workflow (what works today, and what it becomes), section 5 is the migration plan. Code changes only start after this design is approved.

Who this is for: engineers and pixel artists who will add characters. Stats, AT cost, cooldowns, signature-skill gameplay and balance are out of scope and stay untouched.

---

## 1. How it works today (as built)

### 1.1 Layers

| Layer | Where | What it does |
|---|---|---|
| Art | `public/assets/characters/<id>/<anim>.png` (external) or `assets/characters/<faculty>/<name>/*.png` (generated, 11 heroes) | One horizontal strip of frames per animation state |
| Config | `public/assets/characters/sprites.json` (source of truth, external) and `assets/characters/animations.json/.js` (generated heroes) | Frame size, count, fps, loop, feet row, scale, shadow, impact frames |
| Merge | `public/assets/characters/manifest.js` (generated by `tools/import-sprite.js`) | Overrides the sprite art of listed heroes at load time; combat data is untouched |
| Runtime | `index.html`: `SPRITES`, `loadSprites`, `animState`, `advanceAnim`, `frameIndex`, `drawSpriteFrame`, `corpses` | Picks the state, derives the frame, draws it (nearest-neighbour, feet on `y+24`) |
| Skill presentation | `index.html`: `SKILL_MODE`, `SKILL_FX`, `fx*` helpers | When the skill animation plays, and the hand-written particle effect |
| Tools | `tools/import-sprite.js`, `tools/make-gif.js`, `tools/downscale-sprite.js`, `tools/pixel/art/bug_hunter_*.js` | Import, GIF preview, still-to-animation derivation (Bug Hunter only) |
| Tests | `tests/bug-hunter-anim.test.js`, `hurt-timeline.test.js`, `visual-polish.test.js`, `external-sprites.test.js`, `sprites.test.js` | Per-character art checks plus generic timeline/combat checks |

### 1.2 The seven states

`idle`, `walk`, `attack`, `skill`, `hurt`, `death`, `stun`. Priority in `animState(u)`:

`death > hurt > stun > skill > attack > walk > idle`

A missing sheet falls back to `idle` (`rec.anims[name] || rec.anims.idle`). Bug Hunter is the only hero with all seven.

| State | Bug Hunter frames @ fps | Loop | Clock |
|---|---|---|---|
| idle | 4 @ 6 | yes | accumulates |
| walk | 6 @ 12 | yes | accumulates |
| attack | 6 @ 12.5 | once | `ATK_DUR - atkT` |
| skill | 12 @ 17 | once | `SKILL_DUR - skillT` |
| hurt | 3 @ 12 | once | `HURT_DUR - hurtT` |
| stun | 4 @ 8 | yes | accumulates |
| death | 6 @ 8.5, frame 224x96 | once | corpse age `c.t` |

Attack, skill and hurt clocks are derived from the combat timers, so a state switch can never desync a frame from its combat event (fixed in `6dd6858`; this was the "hurt interrupt" bug).

### 1.3 Timing contract with combat (global constants in `index.html`)

| Constant | Value | Meaning | Sheet rule |
|---|---|---|---|
| `ATK_DUR` | 0.5 s | length of an attack swing (`atkT`) | attack frames / fps <= 0.5 |
| `IMPACT_DELAY` | 0.25 s | projectile launch or melee hit | `floor(0.25 * fps) == impact.attack` |
| `SKILL_DUR` | 0.72 s | skill animation window (`skillT`) | skill frames / fps <= 0.72 |
| `SKILL_IMPACT` | 0.43 s | skill effect moment | `floor(0.43 * fps) == impact.skill` |
| `HURT_DUR` | 0.25 s | hurt reaction | hurt frames / fps ~ 0.25 |
| corpse life | 0.7 s | `corpses.filter(c => c.t < .7)` | death frames / fps ~ 0.7, last frame almost empty |

Choosing the fps (this is why Bug Hunter uses 12.5 and 17): for impact frame `i` at time `T`, `fps` must satisfy `(i + 0.12) / T <= fps < (i + 0.88) / T` (a 0.12 frame safety margin so float error or one lagging tick still shows frame `i`) and `frames / fps <= duration`. Attack 6 frames, `i = 3`: `12.5 <= fps < 15.5`. Skill 12 frames, `i = 7`: `16.6 <= fps < 18.3`.

### 1.4 Data per character today

- `sprites.json`: `scale`, `impact {attack, skill}`, and per anim `file, frameWidth, frameHeight, frameCount, frameRate, repeat, feetRow, shadow[]`.
- `shadow` (per frame `[dx, halfWidth, alpha]`) is computed by `--shadow auto` and lets the ground shadow follow a falling body and fade out.
- `drawSpriteFrame` reads size, scale, feet row and shadow from the anim definition, so frame sizes may differ per animation (Bug Hunter death is 224x96).

## 2. What blocks scaling to 100 characters

Each item was checked in the code; numbers are from this repository.

| # | Finding | Evidence | Consequence at 100 heroes |
|---|---|---|---|
| F1 | Skill effects are hand-written JS per hero | `SKILL_FX` has 12 entries of `run: u => {...}`; `SKILL_MODE` is another 12-entry table; both live in `index.html` | Every new hero edits the game file; no validation; high merge-conflict rate |
| F2 | Anchors are constants | projectile origin `(u.x+18, u.y-14)`, Bug Hunter beam `(u.x+22, u.y-30)` | Bug Hunter only lines up because we designed it to; each new hero's muzzle must be configurable |
| F3 | Two config formats | `animations.json` (generated heroes) vs `sprites.json` (external), merged by `manifest.js` | Two sources of truth, different field sets (impact/shadow only in one) |
| F4 | Config is built one sheet at a time by CLI flags | `import-sprite.js add <id> <png> --anim ...` | Easy to forget `--impact` or `--shadow`; no single reviewable file per character |
| F5 | Art checks are hand-written per character | `bug-hunter-anim.test.js` knows Bug Hunter's face rows and laptop rectangle | Does not scale; a generic validator is needed |
| F6 | Global timing | the constants in 1.3 | Fine while all heroes share timing, but fps must be fitted per sheet and verified; a hero with different swing speed cannot be expressed |
| F7 | VFX uses the battle RNG (fixed in Phase 3, see section 9) | `fxBurst` calls `Math.random`. Measured: same seed, `full` vs `reduced` effects gives different kills, enemy HP and unit positions (kills 10/10, enemy 6307 vs 6295, positions differ) | Visual settings change combat results. Adding many data-driven effects makes it worse. Needs its own seeded RNG before the VFX system is expanded |
| F8 | Fallback is implicit | any missing state silently becomes `idle` | A "complete" character cannot be distinguished from a half-finished one; skill falling back to idle hides a missing signature animation |
| F9 | Every sheet is loaded at page load | `loadSprites()` loops over all heroes (13 heroes x up to 7 files today) | 100 heroes = ~700 image requests before the first screen |
| F10 | Still-to-animation tooling is Bug Hunter specific | `bug_hunter_*.js` hard-code leg rows, laptop rectangle, tuft rectangle | Reusable idea (rigid parts), non-reusable code |
| F11 | Hero roster data is in the game file | `heroes` table and `SKILL_MODE` in `index.html` | Not part of this work (stats are frozen), but the descriptor must not assume it moves |

What already works and should be kept: derived animation clocks, hard-alpha pixel sheets, feet-row alignment, per-frame shadow, impact frames in config, manifest merge, GIF preview, hurt/stun/death state handling, combat-neutral visuals (verified: 96 old-vs-new battles identical).

## 3. Proposed architecture

Principle: **a character is one folder plus one descriptor; everything else is generated or validated.** The game reads generated data only.

```
public/assets/characters/<id>/
  character.json      the single source of truth for this character (hand-edited)
  idle.png walk.png attack.png skill.png hurt.png death.png stun.png
  (optional) rig.json + source/still.png   only for characters derived from one still
```

### 3.1 `character.json` (proposed schema)

```json
{
  "id": "bug",
  "name": "Bug Hunter",
  "faculty": "ICT",
  "sprite": { "frame": [96, 96], "scale": 1, "feetRow": "auto", "facing": "right" },
  "anims": {
    "idle":   { "file": "idle.png",   "frames": 4,  "fps": 6,   "loop": true },
    "walk":   { "file": "walk.png",   "frames": 6,  "fps": 12,  "loop": true },
    "attack": { "file": "attack.png", "frames": 6,  "fps": "fit", "impact": 3 },
    "skill":  { "file": "skill.png",  "frames": 12, "fps": "fit", "impact": 7 },
    "hurt":   { "file": "hurt.png",   "frames": 3,  "fps": "fit" },
    "stun":   { "file": "stun.png",   "frames": 4,  "fps": 8,   "loop": true },
    "death":  { "file": "death.png",  "frames": 6,  "fps": "fit", "frame": [224, 96], "shadow": "auto" }
  },
  "fallback": { "skill": ["attack", "idle"], "stun": ["hurt", "idle"], "death": ["idle"] },
  "anchors": { "muzzle": [18, -14], "skill": [22, -30] },
  "signature": {
    "skillMode": "onStack",
    "fx": { "at": "impact", "ops": [
      { "op": "beam",  "from": [22, -30], "to": [282, -30], "color": "#7fe3ff" },
      { "op": "burst", "at": [24, -30], "color": "#bff3ff", "count": 10, "size": 3 },
      { "op": "shake", "amount": 2 } ] }
  }
}
```

- `"fps": "fit"` means the build tool computes the lowest fps that satisfies the timing contract in 1.3 (impact frame margin and duration fit) and writes it to the generated config. A fixed number is allowed but is validated against the same rule.
- `anchors` are pixel offsets from the unit position, mirrored automatically for enemies. If absent the current constants are used (backward compatible).
- `signature.skillMode` mirrors today's `SKILL_MODE`; gameplay of the skill (what it does, damage, cooldown) stays in the hero table and is not part of the descriptor.

### 3.2 Build tool (`tools/characters.js`, proposed)

`node tools/characters.js build` reads every `character.json`, validates it, computes fps and shadow, and writes the files the game already understands (`sprites.json`/`manifest.js` format, so the runtime needs no rewrite in phase 1). `check` runs validation only; `preview <id>` writes GIFs and a contact sheet (generalising `make-gif.js` and the screenshot scripts used for Bug Hunter).

### 3.3 Runtime changes (small, additive)

1. `anchors` read by `launchProjectile`, muzzle flash and skill FX origin, defaulting to today's constants.
2. Explicit fallback chain from the descriptor (replaces the implicit `|| idle`), plus a one-line console warning in debug builds for a state that falls back.
3. Lazy loading: `ensureSprites(teamIds)` at team confirmation (6 heroes) instead of loading all heroes at page start. `spriteReady` already gates drawing per hero, so this is safe.
4. Optional per-hero atlas (all states in one PNG, rows per state) to cut requests further; only needed if lazy loading is not enough.
5. Per-hero attack/skill durations are **not** proposed now (see open decisions).

### 3.4 Signature skills and unique animation (requirement: not one skill recoloured)

Two separate things, kept separate on purpose:

- **Skill gameplay** (what it does): hero table and skill handlers in `index.html`. Unchanged by this pipeline.
- **Skill presentation** (what you see): the hero's own `skill.png` sheet plus its own FX recipe.

Rules enforced by the validator so recolours cannot slip through:

1. A character that claims `complete` must have its own `skill.png` whose frames are not a palette-swap of `attack.png` or of another character's skill sheet. Check: convert each frame to a binary silhouette plus a normalised-colour mask and compare against all other characters; report a **warning** when most pixels match. It never fails the build and never decides by itself that skills are duplicates (see section 6, item 7).
2. FX recipes must have a unique `kind` across the roster (an existing test already enforces unique kinds for the 12 heroes) and must differ in structure (op list shape and geometry), not only in `color`.
3. `signature.skillMode` and the skill gameplay entry must both exist for the character, so a presentation can never exist without a skill behind it.

### 3.5 Data-driven VFX

Ops map one-to-one onto the existing helpers (`fxBeam`, `fxBurst`, `fxRing`, `fxSpawn`, `fxShake`), with offsets relative to the unit and an `at` timing (`impact` or seconds). The 12 current `SKILL_FX` entries convert mechanically; the loops they use (a row of paw prints, a spiral, a dome arc) need three pattern ops: `row`, `spiral`, `arc`. Anything that cannot be expressed stays as a small custom script `skills/<id>.js` registered by id (escape hatch, validated to run without exceptions).

**Prerequisite (F7):** VFX must use its own seeded PRNG, not `Math.random` of the battle. Today the fx setting changes combat results. Doing this changes the random stream, so combat baselines (test seeds) shift once; it needs your explicit approval.

### 3.6 Automatic validation (`tools/characters.js check`, run in the test suite)

| Severity | Rule |
|---|---|
| error | descriptor matches the schema; every referenced PNG exists |
| error | 8-bit RGBA; alpha only 0 or 255; sheet size = frame width x frames; no opaque pixel on the frame edge |
| error | `idle` exists; every other state either exists or has an explicit fallback |
| error | timing: impact frame is hit at `IMPACT_DELAY` / `SKILL_IMPACT` with the safety margin; frames/fps fit `ATK_DUR`, `SKILL_DUR`, `HURT_DUR`; death ends sparse at the corpse life |
| error | feet row identical across idle/walk/attack/skill/hurt/stun (death rests on the ground line); shadow table length equals frame count |
| error | no new 1 px holes compared with the idle frame; no frame fully transparent |
| error | facing right |
| warn | palette larger than the budget (default 40 body colours plus 12 effect colours) |
| warn | figure height outside the roster band (+-15% of the median) |
| warn | face/identity drift: the head block of attack/skill/hurt/stun differs from idle beyond the allowed expression change |
| warn | skill sheet too similar to attack or to another character (3.4) |
| report | completeness grade: Bronze (idle), Silver (idle, walk, attack), Gold (all seven with unique skill) |
| smoke | the game draws every state of every character without exceptions, and in a headless battle the launch frame equals `impact.attack` |

## 4. Adding a character

### 4.1 Today (works now, per sheet)

1. Draw the 96x96 (or larger) PNG strips: transparent background, hard pixels, facing right, one horizontal row of frames. Follow `docs/BUG_HUNTER_SPEC.md` for the visual standard.
2. Import each sheet:

   ```
   node tools/import-sprite.js add <id> idle.png   --anim idle   --frames 4 --frame 96x96
   node tools/import-sprite.js add <id> walk.png   --anim walk   --frames 6 --frame 96x96
   node tools/import-sprite.js add <id> attack.png --anim attack --frames 6 --frame 96x96 --rate 12.5 --impact 3
   node tools/import-sprite.js add <id> skill.png  --anim skill  --frames 12 --frame 96x96 --rate 17 --impact 7
   node tools/import-sprite.js add <id> hurt.png   --anim hurt   --frames 3 --frame 96x96 --rate 12
   node tools/import-sprite.js add <id> stun.png   --anim stun   --frames 4 --frame 96x96 --rate 8
   node tools/import-sprite.js add <id> death.png  --anim death  --frames 6 --frame 224x96 --rate 8.5 --shadow auto
   node tools/import-sprite.js check
   ```
3. The hero must already exist in the game (hero table and `SKILL_MODE`/`SKILL_FX` in `index.html`); the importer only replaces art.
4. Run `node --test tests/` and preview with `tools/make-gif.js` and an in-game screenshot.

### 4.2 After the pipeline (target)

1. Create `public/assets/characters/<id>/` with the seven PNGs and `character.json`.
2. `node tools/characters.js check <id>` until it reports no errors; read the grade.
3. `node tools/characters.js build` regenerates the game data.
4. `node tools/characters.js preview <id>` produces GIFs, a contact sheet and a headless in-game capture.
5. Add the hero's gameplay entry (stats and skill behaviour, unchanged process) and its FX recipe in `character.json`.
6. Open a pull request; CI runs the same validator.

|---|---|---|---|
| 0 | This document and approval | no | none |
| 1 | `character.json` schema, `tools/characters.js` build and check (generates today's `sprites.json`/`manifest.js`), migrate Bug Hunter's descriptor, generic validator tests; runtime unchanged | no | low |

| 3 | Isolate VFX RNG (F7) | shifts the random stream once | medium; needs approval and a re-baseline of seeded tests |

| 5 | Unify the 11 generated heroes onto the same descriptor (their generator stays as an art source) | no | low |
| 6 | Optional: atlas packing, roster data externalisation | no | low |

Success check at every phase: `node --test tests/` green, `tools/characters.js check` green, and the old-vs-new battle comparison (96 cases including injected stuns and hurts) identical.

## 6. Approved decisions

The architecture was approved with these requirements (they override anything above that reads differently):

1. **Configuration:** one `character.json` per character is the main source for sprites, animation and visual configuration, covering all seven states, frame count and fps, impact frames, sprite dimensions, display scale, feet alignment, projectile anchor, skill VFX anchor, death shadow, fallback and character-specific VFX. Data that must exist in two places (for example the skill mode that also exists in the game) needs an automatic consistency check.
2. **Timing:** the architecture supports per-character attack duration, skill duration and impact timing in the future, but the current characters keep today's values. Combat decides when damage happens; animation follows the combat timeline.
3. **Random numbers:** combat and VFX get separate RNGs. VFX must not consume the combat random stream, so Full/Reduced effects and effects on/off give identical battles, and combat testing is deterministic. Before changing it, record the old system's reference results; afterwards create a new baseline and report the differences. (Phase 3.)
4. **Asset loading:** Phase A lazy loading (only characters needed for the current battle), then Phase B texture atlas only if measurements show fewer requests or better performance.
5. **Existing characters:** the 11 placeholder heroes are not migrated yet; Bug Hunter is the pilot. Others move in batches after the new system is tested.
6. **Hero data:** hero and skill data may leave `index.html` in the future, not now.
7. **Unique skills:** every character needs a signature skill that is unique as a gameplay mechanic. The silhouette check only *warns* about similar animation; the 90% figure must not be used to decide automatically that skills are duplicates.
8. **Priority:** start with Phase 1 only (schema, build and check pipeline).

## 7. Phase 1 as built

Files:

| File | Purpose |
|---|---|
| `public/assets/characters/character.schema.json` | JSON Schema (draft-07) for `character.json`; editors pick it up through `"$schema"` |
| `public/assets/characters/<id>/character.json` | the configuration of one character (Bug Hunter is the pilot) |
| `tools/characters.js` | `build`, `check`, `list` |
| `tools/lib/jsonschema.js` | small dependency-free JSON Schema validator used by the tool (the schema file is authoritative) |
| `tools/lib/game-probe.js` | reads timing constants, the muzzle offset, hero table, `SKILL_MODE` and `SKILL_FX` from `index.html` so duplicated data can be cross-checked |
| `tests/characters-pipeline.test.js` | schema, fit, equivalence, consistency, art checks, stale detection, add-by-config |

Commands (run from the repository root):

```
node tools/characters.js check            # everything: schema, art, timing, consistency with the game, stale files, in-game smoke test
node tools/characters.js check bug        # one character
node tools/characters.js build            # validate, then write sprites.json + manifest.js
node tools/characters.js list
```

How it fits the rest:

- `sprites.json` and `manifest.js` are now **generated** for every character that has a `character.json`; the manifest text still comes from the single generator in `tools/import-sprite.js`. For Bug Hunter the generated files are byte-identical to the ones that were shipped before (checked by a test).
- `check` fails when the generated files are older than the configuration, so they cannot drift.
- `import-sprite.js add/remove` refuse to touch a character that has a `character.json` (one source of truth). Characters without one keep working with the old importer.
- The game and the placeholder heroes are untouched: `index.html`, `assets/characters/**`, stats, skills and balance are not changed in this phase.

Fields the runtime does not read are cross-checked against the game instead of being trusted. Since Phase 2 the runtime reads `anchors` and `fallback`; it does not read per-character `timing` yet; since Phase 4 it plays `signature.fx`. Checks: `timing` must equal the global constants, `signature.skillMode` must equal `SKILL_MODE`, `signature.fx.kind` must equal the `SKILL_FX` kind, `signature.fx` is played by the real engine and must be valid, draw something, use no combat random numbers and have a unique kind (since Phase 4 the effect data is what the game plays; there is no hand-written effect to compare with), and `name`/`faculty` must equal the hero table. Until the runtime reads them, a different value is an error rather than a silent no-op.

Adding a character by configuration only (visuals): put the PNG strips and a `character.json` in `public/assets/characters/<id>/`, run `node tools/characters.js check <id>` then `build`. The hero itself must already exist in the game's hero table (hero data is not externalised yet). A test adds a synthetic character this way and checks that the unchanged game draws it with the right frame, scale and feet row.

Warnings, not errors: palette budget, on-screen height versus the roster median (+-15%), identity drift (colours that do not appear in idle), one-pixel holes in idle/walk/hurt/stun, an undissolved last death frame, and animation similarity (what skill and attack add to the resting figure being almost the same). The similarity figure is a hint for reviewers and never decides anything.

## 8. Phase 2 as built (runtime visual integration)

The runtime in `index.html` now reads the generated configuration. Combat code is untouched.

- **Anchors.** `anchors.muzzle` (projectile spawn and muzzle flash, mirrored for enemies) and `anchors.skill` (skill VFX origin) come from the generated manifest. The defaults `DEFAULT_MUZZLE = [18, -14]` and `DEFAULT_SKILL_ANCHOR = [22, -30]` equal the old hard-coded values. `runSkillFx` passes the origin as a second argument to each effect; Bug Hunter's effect is written relative to it (the other 11 hand-written effects ignore it and are unchanged). Bug Hunter's configured anchors equal the old constants, so projectile and beam positions are the same (tested, and pixel-identical in the browser).
- **Feet, scale, death shadow.** Already data in the generated config (`feetRow`, `scale`, per-frame `shadow`); tests now change the config and check that the drawing follows.
- **Explicit fallback.** `animFor(rec, state)` walks the state itself, then `fallback[state]` from the config, then `idle`. Only `idle` is required; a missing or failed other sheet affects that state only (before, one failed sheet dropped the whole character to the placeholder drawing). Debug mode (`?debug` in the URL, `localStorage woc.debug = 1`, or `setDebug(true)`) prints one `console.warn` per character and state and lists the last fallbacks on the canvas; production prints and shows nothing. `node tools/characters.js check` warns about a missing state that has no explicit fallback chain.
- **Lazy loading.** Nothing is requested at page start. `ensureSprites(ids)` creates the sprite record and requests its sheets once; the record stays in `SPRITES` (the cache). It runs when the team screen is shown or the team changes (prefetch), and again at battle start for the team, its summons (`SPRITE_DEPS`, for example Animal Keeper brings the dog) and the stage enemies (`ENEMY_SPRITE_IDS`; no enemy has a sprite yet). Until a sheet is ready the unit is drawn with the placeholder, so a battle never waits for an asset. The headless test harness loads every configured sprite by default (`{ lazy: true }` switches to the real behaviour).

Measured in a real browser (Edge, default team): image requests at page load went from every configured sheet (about 79) to 0; the team screen requests 43 (default team plus the dog); picking one more hero adds its 6; starting a battle adds none; a hero that is not in the team is never requested.

## 9. Phase 3 as built: separate combat and visual randomness

Finding F7 (visual settings changed combat results) is fixed. For the same battle seed and the same player inputs, the effects level can no longer change the outcome of a battle.

### 9.1 Every random draw, classified

Before the change the game had 12 `Math.random()` calls on one shared stream. Each one, and where it went:

| Where | What it draws | Class | Stream now |
|---|---|---|---|
| `update`: enemy wave timer | which enemy type spawns (`r < .25` tank, ...) | Combat | `crand` |
| `spawnEnemy` | enemy spawn x offset (`968 - r*15`) | Combat | `crand` |
| `bossPhase` | x of each Exam-Paper-Rain warning (`150 + i*180 + r*100`); the warning deals damage there | Combat | `crand` |
| `makeUnit` | unit lane y (`327 +- 15`) | **Ambiguous** (cosmetic state of the simulation) | `crand` |
| `makeUnit` | unit walk-cycle phase (`r*6`) | **Ambiguous** (cosmetic state of the simulation) | `crand` |
| `bumpEnemy` | enemy lane y (`326 +- 12.5`) | **Ambiguous** (cosmetic state of the simulation) | `crand` |
| `damage` | damage-number x jitter | **Ambiguous** (cosmetic state of the simulation) | `crand` |
| `fxBurst` | particle angle, speed, life (3 per particle) | VFX | `vrand` |
| `draw` | screen-shake offset x and y (2 per drawn frame) | VFX | `vrand` |

The five ambiguous draws are decided like this: y, walk phase and damage-number jitter do not influence any gameplay number (hits are decided by x distance only), but they are part of the simulation state, they are drawn at simulation events (a unit being created, damage being dealt) and the amount drawn does not depend on the effects level or the frame rate. Putting them on the visual stream would make unit positions differ between quality levels, because that stream is consumed differently by each level. They therefore stay on the combat stream, which also keeps the order of the simulation draws exactly as it was. The test suite still checks positions including y.

There is no other randomness: no custom random functions, no critical hits, no random targeting, no random skill effects, no random AI choices. Target selection is deterministic (nearest foe). `performance.now` is used only to throttle the statistics panel.

### 9.2 Architecture

```
battle.rng.combat   crand()   seeded; every draw the simulation makes
battle.rng.vfx      vrand()   seeded; only particles and screen shake
battle.seed                  the battle seed; the visual seed is derived from it
```

- `createSeededRng(seed)` is mulberry32. Each stream exposes `next()`, `state` and `draws`, so tests can compare the exact RNG state.
- Seed management: `startBattle(seed)` uses the given seed; otherwise `setBattleSeed(n)` (or `?seed=n` in the URL) if set; otherwise one `Math.random()` call picks a seed. That single call is the only use of `Math.random` left in the game. The visual seed is `seed XOR 0x9e3779b9`, so one number reproduces a whole battle, visuals included.
- Effects levels: `full`, `reduced` (half the particles, no shake) and a new `off` (no particles, no shake). `off` is available through `setFxLevel('off')`; the header button still toggles full/reduced and `off` is not saved to `localStorage`. In `off` the visual stream is not touched at all.
- Combat never draws from the visual stream and the visual code never draws from the combat stream; tests check both directions by source inspection and at run time (including a visual stream that throws when touched).

### 9.3 Intentional difference

The old combat sequence cannot be reproduced. Before, one stream served both purposes and most of its draws were particles (11,141 draws per battle on average before; after the split a comparable battle uses about 620 combat draws and about 9,700 visual ones, roughly 94% visual), so the k-th combat decision received whatever number was left after an effects-level-dependent number of particle draws. There is no seed that gives the old combat numbers back, and the old numbers themselves changed with the effects level. What is preserved is the order and the call sites of the combat draws, and all rules, formulas and stats. Every battle now draws a different (but fixed per seed) set of combat numbers, and a battle no longer depends on the effects level or on how often the screen was drawn.

Recorded evidence (`tests/baselines/`, regenerate with `node tools/capture-baseline.js`, compare with `node tools/compare-baselines.js before.json after.json --md out.md`):

- `phase3-before.json`: 23 scenarios on the old code (6 seeds x 3 teams, 2x speed, pause/resume, boss rain) plus 9 variants. In the old code the same seed gave different kills in every variant that changed the effects level or drew every frame (for example seed 1 mixed team: 16, 17 and 15 kills).
- `phase3-after.json`: the same scenarios and 15 variants on the new code. Every variant, including `off`, is bit-identical to the main run (same digest of every simulation tick).
- `phase3-comparison.md`: per-scenario and aggregate comparison. Over the 23 scenarios the means of kills, damage, defense and healing are within one standard deviation of each other. A separate 120-run-per-build comparison (40 seeds x 3 teams, 90 s) found no statistically significant difference (kills 22.5 vs 22.5, damage 14167 vs 13856, enemy base HP 5389 vs 5274; all |z| < 1.6).

### 9.4 Deterministic testing

`tests/lib/combat-trace.js` runs a scripted battle headlessly (fixed simulation step, inputs at fixed simulation times: deploys, income upgrades, faculty laser, ultimate) and records spawns, projectile launches, boss-rain positions, checkpoints of every unit (x, y, HP), the final DMG/DEF/HEAL statistics, the outcome, the RNG state and a SHA-256 digest of the whole simulation. `tests/rng-separation.test.js` runs the same battle with full, reduced and off effects, with and without drawing every frame, over several seeds and teams, with 2x speed, pause/resume and the boss, and requires every gameplay field and the combat RNG state to match exactly. It also checks that the visual stream really differs between modes (so the comparison cannot pass vacuously) and that the current code reproduces the recorded baseline.

### 9.5 Rules for developers of skill VFX

1. Anything that only changes how a skill looks (particles, shake, flashes, trails) must use `vrand()`, never `crand()` and never `Math.random()`. A test fails if `Math.random` appears anywhere except the seed pick.
2. VFX code must not read or write anything the simulation reads: no HP, positions, timers, cooldowns, target lists, `battle.rng.combat`. Unit fields written only for drawing (`animName`, `animT`, `flashT`) are fine.
3. Do not make gameplay depend on whether a particle exists. Particle counts change with the effects level; the simulation must not know.
4. Randomness that decides a gameplay outcome (where a hit lands, what spawns, who is chosen) uses `crand()`, is drawn at a simulation event (never in `draw()`), and the number of draws must not depend on effects level, frame rate or drawing.
5. Use the `fx*` helpers (`fxBurst`, `fxRing`, `fxBeam`, `fxSpawn`, `fxShake`); they handle the effects levels (`reduced` halves, `off` skips). Effects must not call `draw()`-time randomness for gameplay.
6. A new effect needs no test of its own for determinism; the existing scenarios already compare full, reduced and off. If a new gameplay random draw is added, record a new baseline and say so in the change.

### 10.2 Configuration format

```json
{
  "id": "dental", "name": "Dental Blitz", "faculty": "DT",
  "art": "builtin",
  "anchors": { "skill": [46, -10] },
  "signature": {
    "skillMode": "every3",
    "fx": { "kind": "drill-spiral", "at": "impact",
      "ops": [
        { "op": "spiral", "at": [0, 0], "count": 16, "angleStep": 0.9, "radius0": 4, "radiusStep": 1.6, "squash": 0.6, "life": 0.35, "colors": ["#73ddff", "#fff"], "size": 3 },
        { "op": "beam", "from": [-24, 0], "to": [24, 0], "color": "#c8d1ee" },
        { "op": "shake", "amount": 1 } ] }
  }
}
```

- `anchors.skill` is the origin of the effect relative to the unit (x mirrored for enemies); every coordinate inside `ops` is relative to it, so moving the anchor moves the whole effect.
- `kind` names the effect (unique per character); `at: "impact"` means it plays at the skill impact moment decided by combat (`SKILL_IMPACT`, 0.43 s).
- `art: "builtin"` marks a character that still uses the generated placeholder art; it has no `sprite`/`anims` yet. Characters with imported sheets (Bug Hunter) have `sprite` and `anims` instead, and the same `signature`.
- `node tools/characters.js build` validates everything against `character.schema.json` and writes `public/assets/characters/fx.js` (`CHARACTER_FX`), which `index.html` loads before the game script. `fx.js` is generated, never edited by hand; `check` fails if it is stale.
- `signature.skillMode` is still cross-checked against `SKILL_MODE` in the game (when a skill plays is gameplay, not presentation).

### 10.3 Rendering primitives (the engine)

The engine is `runFxOps` in `index.html`. Primitives only call the visual helpers, which only draw and only use the visual random stream.

| `op` | What it renders | Main parameters |
|---|---|---|
| `beam` | straight line of pixels | `from`, `to`, `color` |
| `burst` (Particle Burst) | particles flying outward in random directions (visual stream) | `at`, `color`, `count`, `size` |
| `shockwave` (alias `ring`) | expanding ring | `at`, `color`, `radius` |
| `explosion` | shockwave + burst + optional shake in one op | `at`, `color`, `color2`, `radius`, `count`, `size`, `shake` |
| `aura` | particles orbiting and rising around a point | `at`, `color`, `radius`, `count`, `rise`, `life`, `size` |
| `trail` (Projectile Trail) | fading particles along a segment | `from`, `to`, `color`, `count`, `life`, `size` |
| `flash` (Screen Flash) | full-screen colour that fades | `color`, `alpha`, `duration` |
| `dissolve` (Pixel Dissolve) | pixels rising and fading inside a rectangle (visual stream) | `at`, `w`, `h`, `color`, `count`, `life`, `size` |
| `spawn` | one particle, full control | `at`, `v`, `life`, `color`, `size`, `grav` |
| `spiral`, `arc` | particles on a spiral / circular arc | see the schema |
| `repeat` | repeats a list of ops with an offset per repetition | `count`, `step`, `ops` |
| `shake` | screen shake (full effects only) | `amount` |

The 12 current skills use `beam`, `burst`, `shockwave`, `spawn`, `repeat`, `spiral`, `arc` and `shake`. `explosion`, `aura`, `trail`, `flash` and `dissolve` are new primitives available to future skills; they are tested but not used by an existing character, so no existing look changed. Effects levels: `reduced` halves bursts, auras, trails and dissolves and weakens the flash; `off` draws nothing and does not touch the visual stream.

### 10.4 Adding a skill effect for a new character

1. Make sure the gameplay exists first (hero entry and `SKILL_MODE` in `index.html`; those are not data-driven yet).
2. Create `public/assets/characters/<id>/character.json` with `id`, `name`, `faculty` equal to the hero, `art: "builtin"` (or `sprite`/`anims` when you have sheets), `anchors.skill` and `signature` with `skillMode`, `fx.kind` (new, unique) and `fx.ops`.
3. Run `node tools/characters.js check <id>`; fix errors until it reports none, then `node tools/characters.js build`.
4. Look at it in the game (or use the browser capture below), then run `node --test tests/`.

No change to `index.html` is needed. If a skill needs something none of the primitives can draw, add a primitive to the engine once (with a test) and use it from data; do not add character-specific code.

### 10.5 Testing VFX

- `node tools/characters.js check` plays every effect with the real engine at full / reduced / off and reports errors for: invalid data, drawing nothing, combat random draws, particles when off, more particles in reduced than full, a duplicate `kind` (error), and an effect with the same structure as another one differing only in colour (warning).
- `node tools/map-skill-fx.js` prints the table above for the current code; `node tools/compare-skillfx.js` compares every effect with the snapshot of the hand-written originals (calls, particles, visual draws, shake, reduced/off).
- `tests/vfx-engine.test.js`: the 12 effects equal the originals; all 12 activate once at `SKILL_IMPACT`; effects change no HP/stat/AT, call no `damage`, draw no combat random number; every primitive draws, honours reduced/off, mirrors for enemies, uses only the visual stream; nothing stays active (particles, flash, shake all expire); pause freezes effects and 2x ages them twice as fast.
- `tests/rng-separation.test.js` and the Phase 3 baselines: full/reduced/off battles stay identical (skills fire throughout them).
- Browser: seed a battle, deploy a hero, fix its position, call `runSkillFx` and screenshot after a fixed number of ticks (the capture helper used for the migration is described in the Phase 4 report). The screen-shake offset depends on how many frames the browser draws before the capture, so two captures of the same code can differ by a pixel offset; compare several captures.

### 10.6 Keeping each skill's identity

- The gameplay mechanic of each skill is unique and unchanged; the effect is its visual voice. Effects are not variations of one template: they use different primitives and geometry (a beam, a gear shockwave, a spiral, rows of paw prints, speed lines, a dome arc, rising crosses).
- `kind` must be unique (error) and the structure of two effects must differ (warning when they differ only in colour). This is a hint, never a verdict that two skills are duplicates.
- Describe a skill's imagery in the `notes` or review by what it shows (Bug Hunter: digital beam from a hologram; Mecha: gear-coloured barrier shockwaves; Lab: flask burst in two colours; Animal Keeper: paw prints stampeding; Sound Wave: three concentric sound rings; and so on). Use the repository's real names and abilities; do not copy another character's effect and change the colour.
- Several of the original effects belong to the same family (Lab, Chemist and Nurse are two bursts plus a ring with different geometry, colours and sizes). That is how they were before and it was preserved; new characters should aim for something structurally distinct.

### 10.7 Visual randomness

Same rules as section 9.5. Additionally: primitives never use `crand` or `Math.random` (a test inspects the engine's source), particle counts may differ per effects level but nothing in combat may read them, and `dissolve` is the only new primitive that draws visual random numbers (`vrand`), via the visual stream only.

### 10.8 Migration record

Done incrementally with a comparison after each step against the snapshot of the hand-written effects: (1) Bug Hunter, (2) Mecha Freshy and Lab Maniac, (3) the other nine. After every step the migrated effects were identical (same top-level calls, same particles, same visual draws, no combat draws, same reduced/off behaviour). Final cleanup removed the `SKILL_FX` table and `DEFAULT_SKILL_ANCHOR` from `index.html`.

### 10.9 Intentional differences and limitations

- Particle positions of five effects are computed with the offsets summed in a different order (for example the rows of the paw-print stampede and the three music rings), which can differ from the original in the last bit of a floating-point number (below 1e-9 px). Nothing is visible; the comparison tolerance is 1e-9.
- Skill effect anchors for the 11 placeholder heroes live in their new `character.json` files; their art still comes from the generated placeholder sheets.
- `anchors.muzzle` (projectile origin) is still only configurable for characters with imported sheets; the placeholder heroes use the default.
- The roster and `SKILL_MODE` are still in `index.html` (Phase 6).
